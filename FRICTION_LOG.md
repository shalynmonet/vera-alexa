### 6. A presigned-URL call with no bucket configured crashed instead of degrading
- **Task attempted:** Making every public function in `vera/cloud_storage.py` safe to call even when `VERA_S3_BUCKET` isn't set (the default for a laptop demo), so callers don't each need their own guard.
- **Steps taken:** Wrote `except (ClientError, BotoCoreError)` around the `boto3` calls in `presigned_url`/`object_exists`, on the assumption that an S3 call with a missing/invalid bucket would raise one of those.

- **What actually happened:** `boto3.generate_presigned_url(Bucket=None, ...)` doesn't raise a `ClientError` at all -- it blows up with a raw `TypeError` from deep inside botocore's internal bucket-name validator, before any network call, which my `except` clause didn't catch.
- **Severity:** major (would have crashed any MCP tool call that touched an S3-flagged cheer the moment the bucket env var was unset or misconfigured)
- **Workaround:** Added an explicit `if not enabled(): return None/False` guard at the top of every public function in the module, instead of relying on exception handling alone.
- **Actionable suggestion:** For `boto3`/`botocore`, a missing required parameter like `Bucket` could reasonably raise a documented `ParamValidationError` (which it does, in general) consistently surfaced as a catchable, typed exception everywhere -- in this case it surfaced as a bare `TypeError` from an internal validator function instead, which is easy to miss when scoping an `except` clause to the documented exception types.

### 8. The real root cause of entry 2's "timeout": an unread subprocess pipe, not call volume
- **Task attempted:** Adding `test_family_cheers_flow`'s new, larger Family Cheers assertions (Phase 6 rebuild: ~25 tool calls in one test) and running the suite.
- **Steps taken:** The test reliably printed its pass/fail result character, then hung -- sometimes for over three minutes -- before pytest could print anything further. Wrote a standalone script replaying the identical call sequence against a manually-started server (logging to a file, not a pipe) -- it completed correctly and quickly, every time, which ruled out the new tool logic itself. The one real difference: `tests/test_mcp_client.py`'s `_server_session` helper starts the server with `stdout=subprocess.PIPE, stderr=subprocess.STDOUT` and never reads `proc.stdout`.
- **Expected:** Entry 2's fix (shorter, focused tests) should have kept every test well under whatever limit caused the original ~300s timeout.
- **What actually happened:** An OS pipe has a small, fixed buffer (commonly 64KB). Uvicorn logs roughly one line per HTTP request; with nobody draining `proc.stdout`, enough log lines eventually fill that buffer, and the next write from the server process blocks -- the server itself hangs mid-request, the client's request hangs waiting for a response, and eventually times out or (worse) the whole thing hangs past any client-side timeout during the next cleanup step. Entry 2's "split into three tests" fix just kept each test's call count below the threshold where this tipped over; this test's ~25 calls (plus whatever the FastMCP/uvicorn stack logs per request now) was enough to cross it again. This is a textbook `subprocess.PIPE` deadlock, not test-call-volume flakiness.
- **Severity:** major (the same underlying bug as entry 2, now understood precisely, and confirmed to resurface as the test suite grows)
- **Workaround:** Changed `_server_session` to `stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL` (the tests never need the server's console output) and made the teardown kill the process outright if a graceful `terminate()` doesn't exit within 5 seconds. Reran the full suite and the previously-hanging test five times in a row with no hang.
- **Actionable suggestion:** Whenever a test harness captures a child process's stdout/stderr with `PIPE`, something must actually read it (or redirect to `DEVNULL`/a file) -- otherwise the buffer-fill deadlock is a when, not an if, as the process's own logging grows over the life of a project.

### 9. Nova called log_activity on stated intent, not a completed activity
- **Task attempted:** A user said "yes I will walk today, that sounds good" and Nova immediately called `log_activity`, completing the weekly goal and triggering a family cheer -- for a walk that hadn't happened yet.
- **Steps taken:** Reviewed the system prompt (`web/bedrock_chat.py`): it told Nova to call `log_activity` for "anything else they did on their own... like 'I walked for 20 minutes'" but never distinguished that example (past tense, clearly finished) from future or conditional phrasing. Nothing stopped Nova from treating "I will walk" the same way.
- **Expected:** Only a clear statement that something already happened should ever log it.
- **What actually happened:** The model-only approach (a system prompt) has no hard backstop -- a single misread of tense silently credits something that didn't happen, with no error and no way for the rest of the app to tell the difference from a real completion.
- **Severity:** major (silently falsifies the fitness log and can trigger a real milestone/cheer for nothing)
- **Workaround:** Added a second, independent layer: `log_activity`/`log_completion` now require `completed` and `user_statement` on Nova's conversational path, and `server._completion_guard_error` refuses the call (with a message telling Nova what to do instead) when the statement reads as a future plan without a clear completion, or when `completed` is false. A third layer, `plan_activity`/`get_planned_activities`, gives Nova somewhere correct to put the intent instead, and a natural way to follow up later. UI buttons and media-ended events are unaffected -- they never pass `user_statement`, so the guard never engages for them.
- **Actionable suggestion:** For any tool whose side effect is hard to undo (crediting an achievement, sending a message, spending something), don't rely on prompt wording alone to gate it -- require the model to show its work (the exact phrase it's acting on) in a parameter the server actually inspects, so a misjudgment is independently catchable.

### 10. A caught exception wasn't actually catching anything
- **Task attempted:** Verifying the new guard end to end by sending test phrases through the real Nova chat loop (`check_activity_phrases.py`) against the running MCP server.
- **Steps taken:** One phrase ("I went for a walk") led Nova to call `log_activity` without the required `minutes` argument, which the MCP server correctly rejects as a schema validation error. `web/mcp_bridge.py`'s `call_tool` already wrapped this in `try: ... except mcp_bridge.ToolError`, inside `web/bedrock_chat.py`'s tool loop -- which should have turned it into a normal `{"error": ...}` tool result for Nova to see and recover from.
- **Expected:** A caught `ToolError`, same as every other tool-level error this app already handles gracefully.
- **What actually happened:** The crash reached the top of the script anyway, as an `ExceptionGroup` wrapping the same `ToolError` -- `except mcp_bridge.ToolError` doesn't match an `ExceptionGroup` that merely contains one. The raise was happening inside `mcp_bridge.call_tool`'s nested `async with streamable_http_client(...): async with ClientSession(...):` blocks, and anyio's task group re-wraps an exception that propagates through it while there's still structured concurrency to unwind.
- **Severity:** major (any tool call missing a required argument -- not just this new guard -- would have crashed the whole chat turn instead of letting Nova see the error and recover, with no prior symptom to point at it)
- **Workaround:** Moved the `_unwrap(result)` call (the one place that raises `ToolError`) to after both `async with` blocks have exited cleanly, so the raise happens as a plain exception with nothing left to unwind. `except mcp_bridge.ToolError` now actually catches it.
- **Actionable suggestion:** `anyio`'s automatic `ExceptionGroup` wrapping is easy to forget when a try/except straddles an `async with` for a task group (directly, or nested inside a library's context manager like the MCP client). A linter or doc callout for "this except is inside structured-concurrency scope" would have caught it before it shipped.

### 13. A slow Bedrock greeting kept talking after the person had already left Home
- **Task attempted:** Opening the new Chat screen right after the app loads, before Home's proactive greeting (which calls Bedrock for a daily summary and a memory to mention, so it isn't instant) had finished.
- **Steps taken:** Watched Home's greeting flow (`renderHome()` in `web/static/js/main.js`): `showScreen("home")` kicks it off but never awaits it, so it keeps running as a detached background chain while the person navigates freely. Tapping into Chat before that chain's `await greet(currentUserId)` resolved meant its eventual reply arrived, and got spoken and shown in Vera's speech bubble, *after* Chat had already shown its own welcome -- both messages landed in the bubble in quick succession (one overwriting the other) and sometimes audibly overlapped.
- **Expected:** Only the screen actually on screen should ever get to speak or show a message; a slower background chain started by a screen the person has already left should quietly stand down.
- **What actually happened:** Nothing tied a `say()` call back to "is this still the active screen?" -- a detached async chain had no way to know navigation had happened, so it (and the stale speech bubble it worked with) outlived the screen that started it, just as a stale bubble could also outlive ANY screen it was shown on, not just this greeting -- `Companion.placeInScreen()` moved the companion between screens but never cleared or stopped what it had last said.
- **Severity:** major (the exact kind of "the voice assistant doesn't know what it's doing" moment this project's whole design is trying to avoid for an older user)
- **Workaround:** Two complementary fixes in `showScreen()`: (1) a `navToken` counter bumped on every navigation, captured by `renderHome()` before its slow greeting chain begins, checked again before that chain speaks/shows anything -- a stale chain still updates `conversationHistory` (it really happened) but skips speaking and showing it; (2) `showScreen()` now calls `stopSpeaking()` and clears the bubble (`Companion.showBubble(null)`) on every navigation, before the leaving screen's own cleanup (so an intentional farewell message, like stopping a meditation early, still plays normally) -- fixing the bubble-persistence half of the bug generally, not just for this one greeting race.
- **Actionable suggestion:** A screen-transition router that fires-and-forgets async work per screen needs *some* way for that work to check "am I still relevant?" before producing a user-visible side effect (speaking, updating shared UI) -- a monotonically increasing token captured at the start and compared before each side effect is a small, general pattern for that, cheaper than threading an AbortController through every call.

### 14. Starting a game from Chat silently kicked the person out of the conversation
- **Task attempted:** Saying "I'm down for a memory game" from the new Chat screen, mid-conversation.
- **Steps taken:** `handleBedrockToolCalls` (`web/static/js/main.js`) already special-cased every game tool call with `showScreen("memory")` etc., written for the ordinary case of the Games screen's own tiles starting a game. - **Actionable suggestion:** When a tool-call dispatcher's handling of a tool assumes a specific caller context (here: "a game tool call always means navigate to that game's screen"), that assumption is worth stating in a comment at the point it's made, not just in how the code happens to behave -- it's exactly the kind of implicit coupling that breaks quietly the first time a second caller (a new screen, a new flow) shows up.

### 15. Authenticating the MCP server almost leaked a socket per tool call
- **Task attempted:** Adding the `VERA_MCP_TOKEN` bearer-auth gate to `server.py`'s `/mcp` endpoint (production hardening before public hosting), and making `web/mcp_bridge.py` send that token on every call.
- **Steps taken:** The MCP SDK's `streamable_http_client(url, http_client=...)` takes an optional pre-configured `httpx.AsyncClient` for exactly this -- custom headers. The natural-looking first draft built a fresh `httpx.AsyncClient(headers={"Authorization": ...})` inside a small helper function and called that helper at the top of every `call_tool()`/`list_tools()` invocation.
- **Expected:** Each call gets an authenticated client; nothing to clean up, same as not passing `http_client` at all.
- **What actually happened:** Checked the SDK's own source first (good instinct, this one would've been a slow leak rather than an obvious crash): `streamable_http_client` only manages the lifecycle (closes it on exit) of a client it creates itself -- "Only manage client lifecycle if we created it." A caller-provided client is deliberately left open, on the assumption the caller intends to reuse it. Calling my helper fresh on every `call_tool()` would have created a brand new connection pool per call and never closed any of them -- not a crash, just a slowly growing count of open sockets/file descriptors, the kind of thing that looks fine in every manual test and only shows up as resource exhaustion after the server's been running a while under real traffic.
- **Severity:** major (a production-only, time-delayed resource leak -- exactly the category of bug that's cheap to prevent and expensive to diagnose after the fact)
- **Workaround:** Made the authenticated client a single module-level singleton (`web/mcp_bridge.py`'s `_HTTP_CLIENT`, built once at import time, reused by every call, never explicitly closed -- acceptable since it should live exactly as long as the web app process does).
- **Actionable suggestion:** Before passing a "bring your own client/connection" parameter to any SDK function, check what the SDK does with the object's lifecycle, not just whether the call signature accepts it -- "optional pre-configured client" phrasing alone doesn't say who's responsible for closing it, and guessing wrong here fails silently rather than loudly.

- **Expected:** "Copy link for Shalyn" -- her own name, the thing someone browsing the dashboard actually needs to tell whose link they're about to copy.
- **What actually happened:** The button's label (`web/static/js/caregiver.js`) read `m.nickname || m.name` -- the nickname is what Shalyn calls the *recipient* (Rose), not her own name -- so it read "Copy link for Granny," meaningless to anyone trying to find Shalyn's specific link among several family members.
- **Severity:** minor (a labeling bug, not a broken link, but in the exact UI meant to make "whose link is this" unambiguous)
- **Workaround:** Pointed the label at `m.name` instead. The same nickname/name confusion resurfaced independently in two more places shortly after (entries 20 and the cheer-sender-name half of this session's work) -- see entry 20's actionable suggestion for the general fix.
- **Actionable suggestion:** n/a here (own code) -- see entry 20.

### 19. Cheer recordings showed "Error" in preview on iPhone Safari
- **Task attempted:** Recording a family cheer (audio or video) on an iPhone, through Safari, via the `/cheer/<token>` link.
- **Steps taken:** Recorded normally, then the preview/send screen's player showed "Error" instead of playing back what was just recorded. Traced `cheer-record.js`: it hardcoded the `MediaRecorder` output's `Blob` type, and the upload's filename, as `webm`, unconditionally.
- **Expected:** Whatever format the browser actually recorded in should play back in its own preview player.
- **What actually happened:** iPhone Safari's `MediaRecorder` only ever produces `audio/mp4` or `video/mp4` -- never webm -- so the file was genuinely mp4 bytes mislabeled as webm, which no player can decode correctly.
- **Severity:** major (broke cheer recording -- a centerpiece feature -- for every iPhone Safari user, the primary device this app was built to be used from)
- **Workaround:** Two layers. Client: `MediaRecorder` is now created with the first `mimeType` it actually reports supporting (`MediaRecorder.isTypeSupported`, preferring mp4 then webm/opus), and the Blob/filename use `recorder.mimeType` -- what it really recorded, never assumed. Server: every upload (mp4, m4a, mov, webm, anything else audio/video) is transcoded with `ffmpeg` to one universal format (`vera/media_convert.py`: H.264+AAC `.mp4` for video, AAC `.m4a` for audio) before saving, so a cheer recorded on one device plays correctly on any other, and duration is checked against `ffprobe`'s own measured value rather than trusted from the client. Falls back to saving as-is if ffmpeg/ffprobe aren't installed, and both deploy scripts now install ffmpeg.
- **Actionable suggestion:** Never hardcode a `MediaRecorder` output format -- always read `recorder.mimeType` after creation, since the actual format is both device- and browser-dependent and the API gives no way to request a specific one reliably across platforms. For anything accepting arbitrary user-recorded media across unknown devices, converting server-side to one canonical format (rather than storing whatever each device happened to produce) avoids an entire class of cross-device playback bugs at once.

### 20. A cheer's sender name showed the recipient's nickname for them, not the sender's own name
- **Task attempted:** A family member (Shalyn, whose nickname for the Vera user Rose is "Granny") recorded a cheer; Rose was shown "A message from Granny" instead of "A message from Shalyn."
- **Steps taken:** Traced the cheer save path (`add_cheer` in `server.py`) to `family.display_name()`, which returns what the *sender* calls the recipient -- correct for wording addressed *to* a family member (an email nudge, their own setup page), but being reused here to label who a cheer is *from*, to the recipient.
- **Expected:** Rose should always see the sender's own name as whose cheer it is, regardless of what that sender privately calls her.
- **What actually happened:** One function, `display_name()`, was being used for two different directions of the same relationship -- "what to call them" vs. "who this is from" -- and only one of those directions is ever correct for a sender label.
- **Severity:** major (misattributes a deeply personal feature -- a cheer from a specific loved one -- to the wrong name, exactly the kind of mix-up this app exists to prevent)
- **Workaround:** Added `family.sender_name()`, returning the member's own `name` field, used anywhere a cheer's sender is shown to the recipient; `display_name()` is now reserved for the opposite direction only, with both functions' docstrings cross-referencing each other and naming this exact bug so it can't silently recur. A self-healing migration (`_migrate_legacy_cheer_occasions`, run whenever cheers are read) corrects any cheer already saved with the wrong stored name. Also relabeled the family setup/edit screens ("Your name" vs. "What do you call Rose?", each with an example) so the two fields are harder to confuse when entering them in the first place.
- **Actionable suggestion:** When a single real-world relationship has two directions that both need a name (what X calls Y; what Y should call X), don't reach for one shared helper for both -- name them for their direction explicitly (`sender_name` vs. `display_name`, not `get_name` used two ways) so a reviewer -- or a future change -- can't reuse the wrong one by looking only at the return type.

### 21. A locked "before meditation" cheer played immediately, like an anytime cheer
- **Task attempted:** A family member recorded a cheer and picked "Enjoy your meditation" as the occasion it should play for; the very next time the app was opened (no meditation involved), it played anyway.
- **Steps taken:** Traced the unlock logic: every suggested occasion besides milestone/anytime shared one generic `activity` `cheer_type`, which unlocked the moment that activity type had *ever* been logged by the recipient -- including activity already in weeks of seeded demo history, long before the cheer was even recorded.
- **Expected:** A cheer tied to "before meditation" should stay locked until an actual meditation session is about to start, not unlock based on history that predates it.
- **What actually happened:** The unlock model only ever asked "has this activity type happened at all," never "is this activity happening right now" -- so a freshly recorded occasion-specific cheer could unlock (and, through the normal app-open cheer rotation, play) before its occasion had ever actually occurred again.
- **Severity:** major (defeats the entire purpose of letting a family member target a specific moment -- the cheer arrives generically instead, same as any other unlocked cheer)
- **Workaround:** Replaced the one shared "activity" type with real, specific occasions, each firing atomically (unlock and play in the same step, never passing through a separately-unlocked state that the generic rotation could pick up early): `before_session` fires inside `start_meditation`/`start_stretch_routine`, right before that session's own narration begins; `before_activity` fires in a new `start_timed_activity` tool or via `plan_activity`; `after_game` fires immediately after any of the four games finishes scoring. The existing daily cap still applies -- if already hit, an occasion cheer stays locked entirely rather than leaking into the generic app-open pickup, so it only ever plays at its own moment or not that day at all.
- **Actionable suggestion:** "This type of thing has happened before" and "this type of thing is happening right now" are different conditions and need different triggers -- modeling a time-sensitive unlock as "has the category ever occurred" will always risk firing against unrelated history, especially once any seeded or pre-existing data is involved.

### 22. iPhone Safari's speech recognition routinely never marked a result "final"
- **Task attempted:** Using voice input on iPhone Safari -- the live transcript showed the spoken words correctly the whole time, but finishing always produced "I didn't quite catch that. Try again, or type instead."
- **Steps taken:** Traced `startListening()` (`web/static/js/speech.js`): it only ever resolved with `finalTranscript`, built exclusively from results the recognizer marked `isFinal`.
- **Expected:** Whatever text was shown live on screen should be exactly what gets used once listening ends, since that's what the person saw and confirmed by waiting.
- **What actually happened:** iOS Safari's `webkitSpeechRecognition`, in continuous mode, routinely never sets `isFinal` on anything at all -- so `finalTranscript` stayed permanently empty there even on a long, clearly-heard sentence, and every voice turn ended in the generic "didn't catch that" message regardless of what was actually said.
- **Severity:** major (silently breaks voice input -- the app's primary intended input method -- on the exact platform (iPhone) this project is built for)
- **Workaround:** Now tracks the fullest text actually displayed (`finalTranscript`, or the latest interim text if nothing was ever finalized) and resolves with that on finish, whichever path triggered it. Resolves `null` -- the one case that still shows "didn't catch that" -- only when nothing was ever displayed at all. Fixing this surfaced a second, related bug: iOS reissues a non-final result *cumulatively* (each one repeats the prior words plus whatever's newly heard, rather than handing over just the delta), so the old `interim +=` concatenation would have doubled up the overlap once results stopped being dropped; changed to keep only the latest result in a batch.
- **Actionable suggestion:** Don't treat a speech API's "final" flag as the only trustworthy signal of what was said -- on at least one major mobile browser it may never fire at all in continuous mode, so a robust integration needs to track and trust the best *displayed* transcript as a first-class fallback, not an edge case. (Later extracted into [patient-listener](https://github.com/shalynmonet/patient-listener), a standalone library, exactly so this fix doesn't have to be rediscovered per project.)

### 23. The mic looked like it was listening on iPhone but captured nothing
- **Task attempted:** Tapping the mic on iPhone -- it visibly "bounced" into its listening animation but no audio was ever captured; no transcript, no error, nothing.
- **Steps taken:** Traced `captureSpeech()` (`web/static/js/main.js`): whenever Vera was still talking (easy to hit right after the proactive greeting), it `await`ed `veraSpeakingDone` before calling `startListening()`.
- **Expected:** An `await` that resolves almost immediately once she stops talking shouldn't meaningfully change anything about whether the mic works afterward.
- **What actually happened:** iOS Safari only actually engages the microphone when `SpeechRecognition.start()` runs synchronously, within the same call stack as the user's own tap gesture. Any `await` in front of it -- even one settling in milliseconds -- drops the call out of that gesture context, so recognition silently "starts" without ever capturing audio, and the listening UI (a CSS animation) has no way to know anything is wrong.
- **Severity:** blocker (voice input didn't work at all on iPhone -- not degraded, not occasionally flaky, completely non-functional -- with zero error signal pointing at the cause)
- **Workaround:** Removed the `await` in front of `startListening()` entirely -- `captureSpeech()` now interrupts her (synchronously, from the same tap) rather than waiting for her to finish, so the call reaches `startListening()` with nothing awaited in between. Added a regression guard (`tests/test_mic_tap_synchronous.py`) that reads the real source and fails if any `await` reappears between the start of `captureSpeech()` and the `startListening()` call -- confirmed it actually catches the original bug by running it against the old awaiting code before confirming it passes against the fix.
- **Actionable suggestion:** For any browser API whose docs mention "must be called from a user gesture," audit every call site for `await`s between the gesture and the call, not just whether the call itself is reachable from a click handler -- an `await` that resolves near-instantly is invisible in testing on a desktop browser (which has no such restriction) and only fails, silently, on the specific mobile browser that enforces it.

### 24. Fixing entry 23 made Vera go silent for every reply after the first interruption
- **Task attempted:** Verifying the entry 23 fix (interrupting Vera's speech on a mic tap) didn't introduce anything new.
- **Steps taken:** After that fix shipped, voice input itself worked, but Vera stopped speaking her replies entirely after the first time she was interrupted -- text replies kept arriving normally, audio never resumed. Traced `stopPolly()` (`web/static/js/polly.js`): it called `currentAudio.pause()` directly on the `<audio>` element.
- **Expected:** Stopping her mid-sentence should cleanly end that one utterance and leave the app ready to speak the next one normally.
- **What actually happened:** `<audio>.pause()` does not fire the element's `onended` event -- so the `Promise` `speakPolly()` had returned (awaited by `say()`, whose own `finally` block resets the `veraSpeaking` flag) hung forever the instant anything stopped her early. A mic tap now did that routinely post-entry-23, so `veraSpeaking` got stuck `true` after the very first interruption, and every `say()` call after that silently awaited a promise that would never resolve.
- **Severity:** major (total, silent loss of voice output after the first ordinary interaction -- compounding a fix for one input bug into a worse output bug, both on the device this app is built for)
- **Workaround:** Gave `stopPolly()` a proper internal closure that resolves the in-flight promise and fires `onEnd`/`onMouthClosed` the same way a natural ending does, instead of pausing the element and abandoning the promise. Also removed entry 23's interrupt-on-tap behavior as a second line of defense, since letting the mic open while she's still talking (rather than cutting her off) turned out not to require interrupting her at all. Added `tests/polly_stop_check.mjs`/`tests/test_polly_stop.py`, covering an early stop resolving and firing callbacks, a second `speakPolly()` call resolving an in-flight first one, and natural completion still working.
- **Actionable suggestion:** Any wrapper around a browser media element needs to audit every way playback can stop (natural end, explicit stop, a new playback starting) against every event the code depends on (`onended` specifically) -- `.pause()` alone silently skips the one event most promise-based playback code is built around, and the gap only shows up once something actually calls `pause()` from outside the element's own normal lifecycle, which a quiet, single-utterance test run won't exercise.
